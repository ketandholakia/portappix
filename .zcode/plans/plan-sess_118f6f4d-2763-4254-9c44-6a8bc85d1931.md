# Portappix Security Remediation Phase 2 — Plan (R9–R14 + P3)

## Context

The second-pass independent audit (static inspection of the committed source) found six new defects in the Phase-1 remediation: schema-1 HMAC downgrade (R9), incomplete handle-based rename protection (R10), a missing-launcher crash window between the two renames (R11), a cross-process review-metadata race (R12), non-concurrency-safe/non-crash-safe DPAPI key creation (R13), and companion files not restored by watchdog rollback (R14), plus four P3 observations. Verdict: NO-GO pending this phase. Per the audit's methodology and your confirmation: **each defect is first reproduced by a deterministic failing test, then fixed**, then full validation + commits + push (as round 1).

Confirmed decisions: R11 = finalize helper + `ReplaceFileW`; R9 = conditional rejection with blob-backed establishment + fail-closed advisory flag; all four P3 items; repro-first delivery with commit + push.

## Phase A — Deterministic reproductions (must FAIL on current code)

New TESTINJECT seams (compile-time isolated, as established): `PortappixWriteDelayMs` (write-hook sleeps before returning — widens race windows deterministically), `PortappixKeyCreateHook` (sleep inside `GetRollbackKey` creation), `PortappixUpdateCrashPoint` (raises `EPortappixSimulatedCrash` at named update-swap phases, e.g. `swap:after-rename-old` — no-op in production).

|---|---|---|

## Phase B — Fixes

### R9 — `src/Portappix.RecordAuth.pas` + `src/Portappix.Update.pas`
- Blob format v2: magic + version + flags(`Migrated`) + 32-byte key; tolerant read of the v1 legacy blob (treated as key + established — v1 only ever wrote schema-2 records).
- Blob existence = "authenticated schema-2 operation established". Schema-1 acceptance requires blob absence. At establishment (first schema-2 record write or migration re-stamp), also write unauthenticated advisory flag `Cache\rollback_migration.flag`; if that flag exists while the blob is missing → **refuse rollback entirely** (fail closed, no downgrade).
- Split `GetRollbackKey` / `TryGetRollbackKey`: verification paths refuse on a missing key (never mint); only `RecordOldLauncher` and the migration re-stamp may create.
- Residual (blob+flag both deleted by a write-only attacker re-opens a bounded migration window) documented in `UPDATE_ROLLBACK_INTEGRITY.md`.

### R10 — `src/Portappix.Update.pas`
- `OpenVerifiedOldLauncher`: open with `GENERIC_READ | DELETE`, share mode `FILE_SHARE_READ` only (no write/delete share) — external rename/delete becomes impossible during the window.
- Replace the by-path rename with a handle-based rename: `SetFileInformationByHandle(FileRenameInfo)` (declare `FILE_RENAME_INFO` locally) while the handle is open; `ReplaceIfExists = False` (target absent after the `.failed_*` move); fail closed otherwise.
- Post-fix test: external rename attempt fails; rollback succeeds via the handle rename; verified content = moved content.

### R11 — `src/Launcher.dpr` + `src/Portappix.Cli.pas` + `src/MainForm.pas` + `src/Portappix.Update.pas`
- New flow: `PrepareUpdate` stages everything (backups, record, pending, stale-`.old` removal) but does **not** swap; it spawns `launcher_new\Launcher.exe --finalize-update` and the caller **exits** (CLI: dedicated exit code; GUI: orderly close — both call sites updated).
- `--finalize-update` (new CLI command): waits for parent exit; acquires the launcher single-instance mutex (bounded retry, else defer cleanly — pending remains for the recovery respawn); performs the swap atomically via `ReplaceFileW(Launcher.exe ← launcher_new\Launcher.exe, backup = Launcher.exe.old, REPLACE_EXISTING)` — the launcher never goes missing; moves companion root files; moves the backup dir to persistent `Cache\companion_rollback\` (R14); spawns `--post-update`; exits.
- Recovery: on launcher startup (GUI watchdog + CLI dispatch), an unfinalized pending (`update_pending.json` + `launcher_new\Launcher.exe` present + swap not done) respawns the finalize helper once per launch (bounded, logged) — the audit's "recovery bootstrapper".
- `RestoreFailedSwap` retained for helper-side failures (ReplaceFileW is atomic: failure leaves the target intact).
- Fixture/gate adaptation: `PORTAPPIX_CRASH_STARTUP` exempted for `--finalize-update` (so the 1.3.0-fail fixture finalizes the swap, then the `--post-update` instance crashes → watchdog rollback — Gate-3 semantics preserved); `run_selfupdate_validation.ps1` waiting/assertion logic updated for the two-process flow (investigated and adapted during implementation).

### R12 — `src/Portappix.State.pas`
- New review-scoped **named** mutex (`MutexNameFor('Review', root)`), acquired inside `ListReviewItems`, `RecordReviewItem`, `ClearReview` (inner order: `FSync` → review mutex; Windows mutexes are thread-recursive so the nested call from `RecordReviewItem` and the `BeginTransaction` path is safe; 5 s timeout → `EPortappixJournalBusy`).
- The file-existence check moves inside the lock.

### R13 — `src/Portappix.RecordAuth.pas`
- Key creation under a named mutex (`MutexNameFor('RecordKey', key-path hash)`); double-check existence after acquisition; create-new semantics (loser of the race reads the winner's blob); the blob written via the durable temp+flush+`MoveFileEx(WRITE_THROUGH)` pattern (reusing `WriteTextFileDurable`); decrypted length validated (already present).

### R14 — `src/Portappix.Update.pas`
- On successful finalize, the root-file backups survive in `Cache\companion_rollback\`; `ConfirmUpdate` deletes it (update confirmed healthy); `RollbackToOldLauncher` restores companion files from it (checked moves) before deleting it; stale `companion_rollback` dirs cleaned by the recovery path.

### P3 observations
- `WriteTextFileDurable`: delete the temp file on every failure exit (currently left behind after flush/verify failures); tests assert no `.tmp` leftovers after injected failures.
- `whFailAfterTemp` uses the same PID/counter temp naming as the durable writer.
- `ReadPendingVersion`: `channel` (string when present), `appliedAt` (strict ISO-8601 when present) — invalid ⇒ no pending (logged), same policy as `toVersion`.
- Key scope: documentation corrected to **per-user-account** (shared across portable installs of the same account), rationale added; "per-installation" wording removed from report/docs.
- Archive hygiene: new `scripts/make_source_archive.py` producing a clean `git archive`-based source zip (verified with `package_guard.py`) — documents how to hand reviewers binaries-free archives.
